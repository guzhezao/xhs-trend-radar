# 小红书实操细则

按需读取。主流程在 `SKILL.md`，这里是遇到具体卡点时的展开说明。

## URL 模板

搜索页可以自己拼：

```
https://www.xiaohongshu.com/search_result?keyword=<urlencode(关键词)>
```

关键词必须 urlencode。中文直接拼进 URL 在部分环境会被截断。
平台会自动补 `&type=51`，不用自己加。

笔记详情页**不能自己拼**，见下条。

---

## 笔记链接必须带 xsec_token（拼不出来）

小红书笔记详情页受访问签名保护。只有 `note_id` 拼不出可用链接。

实测（2026-07-29，内置 browser）：

| 输入 URL | 结果 |
|---|---|
| `/explore/<note_id>` | 跳 `/404`，`error_code=300031`、`error_msg=当前笔记暂时无法浏览` |
| `/search_result/<note_id>?xsec_token=<token>&xsec_source=pc_search` | 带搜索页原样签名时可正常打开对应详情页 |

`xsec_token` 是平台下发的一次性访问签名，**只能从搜索页卡片的 `href` 属性里读出来**，
不能构造、不能猜、不能复用到别的 note_id 上。

### 正确取法

1. `inspect` 搜索页快照
2. 找 `tag: "a"` 且 `attributes.href` 形如 `/search_result/<note_id>?xsec_token=...` 的元素
3. 把 href 里的 `xsec_token` 原样取出

搜索页卡片 href 里的 `xsec_source` 是空的（`xsec_source=`）。
交付给用户时补成 `xsec_source=pc_search`，实测可正常打开。

### 交付格式

```
https://www.xiaohongshu.com/explore/<note_id>?xsec_token=<原样取出的token>&xsec_source=pc_search
```

`/search_result/<id>` 前缀会被平台 302 到 `/explore/<id>`，token 保留，
所以两种前缀都能开；交付统一用 `/explore/`，用户看着更像正常笔记链接。

### 时效性

token 有有效期（具体时长未实测）。交付时说明"链接由平台签名，可能在一段时间后失效，
失效后按关键词+作者名搜索仍可定位"。**不要**承诺链接永久有效。

## 未登录静默失败（最重要的一条）

未登录访问搜索页，**不会**报错、**不会**跳登录墙、**不会**给验证码。

实测（2026-07-29，`web_fetch` 请求搜索页）：

```
HTTP 200
完整 HTML，含 __INITIAL_STATE__
__INITIAL_STATE__.search.feeds          → []
__INITIAL_STATE__.global.hasWebSession  → false
#global 元素属性                         → data-logged="0"
搜索框 placeholder                       → "登录探索更多内容"
```

页面骨架、导航栏、频道 tab（全部/图文/视频/用户）全都在，
`search-layout__main` 容器也渲染出来了——**里面是空的**。

### 为什么这条要单独拎出来

因为它会骗过所有只看状态码的判断逻辑。一个 `if response.status == 200` 的脚本
会认为抓取成功，然后交付一份"这个关键词最近没什么热点"的空清单。

**用户拿到的不是错误，是错误的结论。**

### 判断与处理

`inspect` 搜索页后拿不到任何笔记卡片时，判断顺序：

1. **先怀疑未登录**——检查是否有登录引导弹层、搜索框 placeholder 是否为「登录探索更多内容」
2. 未登录 → **停下**，告知用户在右侧浏览器完成登录，不要换词重试
3. 确认已登录但确实没结果 → 才考虑是关键词问题，换扩展词再试

**绝不能**因为拿不到结果就直接输出"该词下无高赞内容"。

## 虚拟列表卸载

搜索页是虚拟滚动。`scroll` 之后，视口上方的卡片 DOM 被移除，
此前 `inspect` 返回的 opaque ref 会全部失效，后续动作报"元素不存在"。

处理顺序：

1. 首屏 `inspect` → 记录能拿到的全部卡片（通常 10-20 条）
2. 数量够了就**别滚**，直接进入逐条打开阶段
3. 不够 → `scroll` 一次 → **重新 `inspect`** → 用新 ref
4. 还不够 → 走搜索翻页，或换扩展关键词二次检索
5. 反复滚超过 2-3 次基本是在浪费 token，收益递减且 ref 失效风险上升

---

## 卡片定位：不要按位置取

搜索结果是瀑布流，各列卡片高度不同，
所以**视觉上第 4 个 ≠ DOM 里第 4 个**。按位置序号取 ref 会系统性取错。

正确做法是按内容定位，而不是按序号：

```
# 1. 拿全量快照，里面每个元素带 opaque ref + 可见文本
browser({ action: "inspect" })

# 2. 在快照文本里找到目标标题所属的那个元素，用它的 ref 去点
browser({ action: "click_and_wait_for_navigation", input: { ref: "<该元素的 opaque ref>" } })
```

**ref 只能从 `inspect`（或某个动作返回的快照）里拿，`query` 拿不到可点击的 ref。**
`query` 是读内容用的：`kind:"text"` 读可见文本、`kind:"dom"` 读 DOM 片段，
两者都可以带 `selector` 收窄范围。它适合"确认这页上有没有某段文字"，
不适合"给我这张卡片的句柄"。

而 `selector` 在这个页面上恰好是最不能用的那条路：
页面用 Vue scoped 样式（`data-v-277dd8ed` 这类）加构建 hash 类名，每次发版都会变。
所以定位卡片请用 `inspect` 快照里的可见文本比对，不要写 CSS 选择器。

## 逐条打开

`click_and_wait_for_navigation` 进笔记页后能拿到：

- 完整正文
- 全部标签
- **点赞 / 收藏 / 评论三个数**（这是判断"驱动力"的依据，搜索页卡片上通常只有点赞）
- 发布时间
- 作者昵称与主页链接

拿完 `back` 回搜索页。**注意 `back` 之后列表会重新渲染**，
如果继续用之前的 ref 失败了，重新 `inspect` 一次。

### 为什么必须逐条打开

搜索页卡片只给点赞数。而"驱动力"判断需要赞/藏/评的**比例结构**
（收藏 > 点赞 → 实用型；评论 > 收藏 → 情绪/身份型）。
不逐条打开就只能拿到总量，判断退化成猜。

见 `topic-judgment.md` 第 3.1 节。

## 排序口径

搜索页只给综合排序，我们拿到结果后自己按点赞数重排。

交付时口径必须写成：

> 搜索结果页综合排序前 N 条中，按点赞数重排取前 X

不能写成"小红书点赞前 X"——那是假的，我们没有全站榜单的访问能力。

---

## 互动数实时变动

同一条笔记，隔一段时间刷新互动数会涨。
交付时统一标注抓取时点，不要当成静态事实。

想拿到**增速**（比总量更能判断话题是否还在涨），
唯一办法是同一批笔记隔 24 小时再抓一次做差 —— 用 `mavis cron` 跑两轮。
单次任务里的阶段判断只能标「推断」。

---

## 交叉去重

多关键词检索时同一条笔记会重复出现。去重键优先级：

1. `note_id`（从笔记 URL 取）—— 最可靠
2. 作者 + 标题完全一致
3. 标题高度相似 + 互动数接近 → 人工判断

**记录每条结果来自哪个扩展词。** 这本身是信息——
某个词下面结果少但互动高，说明这个词竞争小。

---

## 频率控制

- 单条笔记抓取之间保持自然间隔（正常人类浏览节奏）
- 单次任务上限 20 条（单关键词建议 10-15 条）。这个数不是保守，是算的：
  每条要 click → inspect 详情 → back → 重新定位 ref 约 4 次动作，20 条约 80 次；
  每次 inspect 都返回一大段页面快照进上下文，再往上会先撑爆上下文再开始丢数据、错配。
  要更多条就拆多轮 / 用 cron 每天跑
- 出现验证码 / 风控提示 → **立即停止**，向用户报告，不尝试绕过
